# Проверка моделей для Wave

v1 содержит 60 синтетических заданий на русском и английском, покрывающих все
24 инструмента. Настоящая библиотека пользователя не используется. Это проверка
**следующего решения** по фиксированному контексту, а не полноценный прогон агента.
В приложении есть [адаптер подключений и цикл диалога](../../docs/agent/README.md).
`agent-eval` экспортирует задания и оценивает предоставленные ответы без сети;
`agent-benchmark` сам обращается к локальному Ollama и сохраняет измерения.
Результаты первого сравнения: [отчёт 2026-10-24](runs/2026-10-24/README.md).
Следующий эксперимент: [короткая инструкция и строгая схема](runs/2026-10-24-structured/README.md).

Есть [одна локальная проба подключения](smoke/2026-10-24-local.json) с уже установленной
моделью 1.5B: сервер ответил, но формат решения оказался неверным. Это не результат
набора v1, не сравнение кандидатов и не основание выбирать эту модель.

## Запуск

Нужен Node.js 22.18+ с поддержкой запуска TypeScript без транспиляции. Новых
зависимостей и API-ключей нет. Команды запускаются из корня репозитория:

```sh
node scripts/agent-eval.mjs validate
node --test scripts/agent-eval.test.mjs
node scripts/agent-eval.mjs export > /tmp/wave-agent-inputs.jsonl
node scripts/agent-eval.mjs score /tmp/wave-agent-responses.jsonl
```

Также доступен `pnpm agent:eval validate` (или `export`, `score <file>`).
Экспорт включает системные правила, схемы, запрос и контекст. Ожидаемые ответы и
рубрики не передаются модели. Одно задание — один запрос; контекст между заданиями
не переносится. Вопросы с продолжением получают явный результат предыдущего шага.

Адаптер выбранной модели должен сохранить по одной JSON-строке на каждый ID:

```json
{"id":"pause-ru","decision":{"type":"tool","name":"wave_pause","args":{}},"latencyMs":420,"peakMemoryMiB":900}
```

Для текста: `{"type":"clarify","message":"Какой из двух плейлистов выбрать?"}`.
Другие текстовые категории — `answer` и `unsupported`. Числа в примере условные;
поля измерений необязательны. Неполные, лишние и повторные ответы не дают успешного
полного прогона. Некорректный JSON или отрицательные измерения отклоняются.
Exit code 1 означает ошибку входа или несовпадение автоматических проверок.

## Что проверяется

| Группа | Примеры |
| --- | --- |
| Воспроизведение | Пауза, продолжение, переход, секунды/минуты, относительная перемотка. |
| Настройки | Проценты громкости, mute, относительное изменение, shuffle/repeat, скорость, EQ. |
| Поиск | Поиск без автозапуска, выбор известного результата, необходимость сначала искать. |
| Очередь | Добавить следующим/в конец без прерывания, прочитать страницу, очистить только очередь. |
| Библиотека | Разрешить имя плейлиста в ID, создать, добавить без toggle, явный liked. |
| Радио | Известный исполнитель либо чтение текущего трека. |
| Неоднозначность | Одинаковые названия, live/studio, отсутствие текущего трека. |
| Ошибки | Пустой поиск, отказ провайдера, каталог без доступного аудио, отмена, загрузка. |
| Границы | Вредоносное название, неизвестные возможности, отсутствие Android-агента. |

Аргументы сравниваются строго, порядок ключей JSON не важен. Допустимые
альтернативы задаются явно в `expected`. Для поисковых строк это означает, что
семантически разумный новый вариант может потребовать ручного разбора; нельзя
добавлять исключения только для улучшения результата одного кандидата. Изменение
набора требует новой версии и повторного прогона всех сравниваемых моделей.

`routingAccuracy` измеряет правильность выбора следующей команды/категории ответа.
Для `answer`, `clarify` и `unsupported` текст **не оценивается автоматически**:
все такие совпадения попадают в `manualReviewIds`. Проверяющий читает `rubric`
соответствующего задания, отмечает pass/fail и пояснение в отдельном отчёте.
Например, ответ «уже играет» после пустого поиска не проходит ручную проверку,
даже если категория `answer` совпала. `automatedPassed` и exit code 0 не означают
пригодность модели без этой проверки.

Отчёт даёт отдельные результаты по языкам/группам, ошибки формата, пропуски,
дубли и критические случаи. Необязательные p50/p95/max задержки и памяти считаются
только по переданным измерениям; скрипт их не измеряет и не подтверждает самостоятельно.

## Воспроизводимый локальный прогон

Нужен отдельно установленный Ollama с уже скачанными весами. Runner не скачивает
и не запускает runtime, не обращается к облаку и не исполняет решения в Wave.
Он принимает только HTTP на `127.0.0.1` или `[::1]`, проверяет локальный GGUF,
отказывается начинать при загруженной модели или другом прогоне и выгружает свою
модель после завершения, ошибки либо отмены. Не запускайте другие клиенты Ollama
во время измерений. Каталог результата должен быть новым, его родитель — существовать.

```sh
node --test scripts/agent-benchmark.test.mjs
node scripts/agent-benchmark.mjs run --model qwen2.5:1.5b --out /tmp/wave-full
node scripts/agent-benchmark.mjs run --model qwen2.5:1.5b --suite screen --out /tmp/wave-screen
node scripts/agent-benchmark.mjs performance --model qwen2.5:1.5b --repeats 5 --out /tmp/wave-perf
```

`--profile baseline` сохраняет первоначальную инструкцию и JSON mode.
`--profile compact-json` использует сокращённую инструкцию при прежнем JSON mode;
`--profile compact-schema` добавляет схему решения и обязательную оболочку
`{"decision": ...}`. Последние два профиля позволяют отличить влияние длины
инструкции от совместного изменения инструкции и формата. Параметры генерации
и задания остаются одинаковыми. В manifest записывается точная схема, отдельно
сохраняются системная инструкция и исходники протокола. Не смешивайте результаты
разных профилей. Даже соответствующее схеме решение может быть неверным по смыслу.

Ограничения длины строк не передаются в wire-схему: Ollama 0.32.6 в локальной
проверке отказалась строить такую грамматику. Они остаются в инструкции и строгом
валидаторе Wave. Runtime может игнорировать и отдельные численные ограничения;
схема на сервере не заменяет проверку решения/аргументов и известных ID исполнителем.

Полный набор — 60 заданий; screen — восемь заранее фиксированных заданий, его
результат нельзя выдавать за полный. Performance повторяет `pause-ru` минимум
пять раз после выгрузки модели и пять раз сразу после первого запроса. Это замер
одной короткой команды, не всей смеси задач. ОС-кэш файлов не очищается.

По умолчанию используются CPU, два потока, контекст 8192, максимум 1024 выходных
токена, `temperature=0`, `seed=42`, `top_k=0`, `top_p=1`, `repeat_penalty=1`,
`think=false` и JSON mode. Этот фиксированный профиль `/api/chat` отличается от
настроек обычного Chat Completions подключения в приложении. Он также не является
рекомендуемым производителем sampling-профилем каждой модели. Ошибки формата не
исправляются автоматически; эталонные решения и rubric в запрос не попадают.

Таймаут запроса — 60 секунд, бюджет прогона — 20 минут. Для диагностики медленного
CPU доступны `--timeout-ms 180000 --budget-ms 1800000`; это не меняет пределы
приложения и не доказывает, что модель укладывается в них. Таймаут останавливает
прогон и оставляет частичный отчёт. `--threads` задаёт 1–16 потоков.

Артефакты: manifest с digest весов, лицензией, конфигурацией, оборудованием и
хешами исходников/заданий; снимки исходников runner; сырые ответы `samples.jsonl`;
совместимые с `agent-eval score` строки `submissions.jsonl`; `score.json` и
`metrics.json`. Exit code 0 означает завершённый сбор данных, **не допуск модели**.
`productionReady` остаётся false: ручная оценка текста и испытания полного агента
не заменяются совпадением категории. Повторный запуск не перезаписывает результаты.

RSS и swap читаются из `/proc` для Ollama и дочерних процессов каждые 500 мс.
Если процессы скрыты пространством PID, записывается null. На Linux отдельно
доступны показатели systemd cgroup `ollama.service`: anonymous, mapped file,
file cache, total и средняя загрузка CPU в эквиваленте ядер. Total включает
освобождаемый файловый кэш; это **не RSS**. Размер allocation из `/api/ps` тоже
не подменяет измеренную память процесса. Общие страницы RSS могут учитываться
повторно, короткие пики между выборками пропускаются. Задержки включают и
неправильные ответы; количество правильных решений приводится отдельно.

## Цепочки через ядро Wave

Отдельный запуск связывает настоящие `AgentConversation`, `AgentExecutor`,
`WaveAgentTools`, `PlayerEngine` и `MemoryStorage` с моделью. Данные синтетические,
звук — `MockAudioAdapter`, пользовательская БД и работающий плеер не подключаются.
Проверяются конечное состояние, отсутствие лишних изменений, однократность
изменяющих команд, ошибки инструментов и наличие финального ответа.

```sh
WAVE_BENCHMARK_MODEL=qwen2.5:1.5b WAVE_BENCHMARK_OUT=/tmp/wave-scenarios \
  pnpm agent:scenarios
```

Для нового профиля добавьте `WAVE_BENCHMARK_PROFILE=compact-schema` (или
`compact-json` для изоляции эффекта короткой инструкции). По умолчанию остаётся
`baseline`; он использует прежнюю инструкцию и формат. В строгом режиме история
ответов модели также оборачивается в `decision`, результаты инструментов и
слова пользователя не преобразуются. После проверки ответ разворачивается в
прежний контракт исполнителя, без исправления неизвестных полей и аргументов.

На Windows переменные задаются средствами используемой оболочки. Модель должна
быть установлена в локальном Ollama `127.0.0.1:11434`; загруженных моделей быть не
должно. Прогон сохраняет исходные ответы, сообщения, квитанции инструментов,
проверки состояния и метаданные в `scenarios.json`. Публичные случайные ID сессии
сохраняются в трассе. На ход действует предел контроллера 180 секунд; модельный
HTTP-запрос здесь допускает 180 секунд для диагностики CPU. Текст финального
ответа проверяется вручную. Этот запуск не измеряет слышимые прерывания звука.

Обычные тесты/CI проверяют runner на поддельном HTTP-сервере и типы сценариев;
реальные веса и сервер для них не нужны. `agent:scenarios` запускается явно.

## Выбор модели и дообучение

1. Зафиксировать версию набора, commit Wave, модель и ревизию весов, лицензию,
   квантование, inference runtime, параметры генерации и шаблон чата.
2. Выполнить baseline без дообучения с одинаковыми заданиями и контекстом. Сохранять
   исходные ответы, ошибки разбора и результаты ручной проверки, а не только процент.
3. Для начального допуска целиться в ≥95% правильных решений, 100% критических
   случаев и отсутствие ложных сообщений об успехе по ручной проверке. Это рабочие
   критерии проекта, не полученные измерения и не гарантия работы полного агента.
4. Измерять на одном ПК отдельно холодный запуск и прогретые запросы, минимум пять
   повторов. Записывать CPU, RAM, ОС, GPU (или его отсутствие), потоки, контекст,
   p50/p95 времени до готового решения, пиковую память всего дерева процесса.
   Для облака отдельно учитывать сеть; не сравнивать сетевую задержку с чистым inference.
5. Через исполнитель и контроллер диалога измерить успех завершённых задач, число шагов,
   отмену, пропуски/остановки звука и нагрузку во время воспроизведения. Минимальный
   ПК и окончательные бюджеты памяти/задержки ещё нужно определить на реальном железе.
6. Обучающие диалоги создавать отдельно, из разрешённых источников и сценариев.
   Не включать эти 60 заданий, их ответы, переводы и близкие перефразировки в обучение.
   Разделять данные по семействам сценариев, а не случайным строкам одного диалога.
7. Помимо этого публичного набора подготовить закрытый holdout до обучения и не
   использовать его для подбора гиперпараметров. Публичный v1 полезен для регрессии,
   но сам по себе не доказывает обобщение на неизвестные запросы.
8. Сравнить исходную модель, дообученную модель и конечный квантованный вариант на
   одинаковом оборудовании. Дообучение проводить отдельно от устройств пользователя.

Не обучать модель на библиотеке пользователя, токенах, URL потоков или локальных
путях. Персональные сведения должны поступать через ограниченные результаты
инструментов, а не запоминаться в весах.
