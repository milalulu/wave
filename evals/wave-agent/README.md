# Проверка моделей для Wave

v1 содержит 60 синтетических заданий на русском и английском, покрывающих все
24 инструмента. Настоящая библиотека пользователя не используется. Это проверка
**следующего решения** по фиксированному контексту, а не полноценный прогон агента.
Модель пока не выбрана; результатов сравнения моделей ещё нет. В приложении есть
[адаптер подключений и цикл диалога](../../docs/agent/README.md), но этот CLI остаётся
автономным: экспортирует задания и оценивает предоставленные ответы без сетевых запросов.

Есть [одна локальная проба подключения](smoke/2026-10-24-local.json) с уже установленной
моделью 1.5B: сервер ответил, но формат решения оказался неверным. Это не результат
набора v1, не сравнение кандидатов и не основание выбирать эту модель.

## Запуск

Нужен Node.js 22.18+ с поддержкой запуска TypeScript без транспиляции. Новых
зависимостей и API-ключей нет. Команды запускаются из корня репозитория:

```sh
node scripts/agent-eval.mjs validate
node --test scripts/agent-eval.test.mjs
node scripts/agent-eval.mjs export > /tmp/wave-agent-inputs.jsonl
node scripts/agent-eval.mjs score /tmp/wave-agent-responses.jsonl
```

Также доступен `pnpm agent:eval validate` (или `export`, `score <file>`).
Экспорт включает системные правила, схемы, запрос и контекст. Ожидаемые ответы и
рубрики не передаются модели. Одно задание — один запрос; контекст между заданиями
не переносится. Вопросы с продолжением получают явный результат предыдущего шага.

Адаптер выбранной модели должен сохранить по одной JSON-строке на каждый ID:

```json
{"id":"pause-ru","decision":{"type":"tool","name":"wave_pause","args":{}},"latencyMs":420,"peakMemoryMiB":900}
```

Для текста: `{"type":"clarify","message":"Какой из двух плейлистов выбрать?"}`.
Другие текстовые категории — `answer` и `unsupported`. Числа в примере условные;
поля измерений необязательны. Неполные, лишние и повторные ответы не дают успешного
полного прогона. Некорректный JSON или отрицательные измерения отклоняются.
Exit code 1 означает ошибку входа или несовпадение автоматических проверок.

## Что проверяется

| Группа | Примеры |
| --- | --- |
| Воспроизведение | Пауза, продолжение, переход, секунды/минуты, относительная перемотка. |
| Настройки | Проценты громкости, mute, относительное изменение, shuffle/repeat, скорость, EQ. |
| Поиск | Поиск без автозапуска, выбор известного результата, необходимость сначала искать. |
| Очередь | Добавить следующим/в конец без прерывания, прочитать страницу, очистить только очередь. |
| Библиотека | Разрешить имя плейлиста в ID, создать, добавить без toggle, явный liked. |
| Радио | Известный исполнитель либо чтение текущего трека. |
| Неоднозначность | Одинаковые названия, live/studio, отсутствие текущего трека. |
| Ошибки | Пустой поиск, отказ провайдера, каталог без доступного аудио, отмена, загрузка. |
| Границы | Вредоносное название, неизвестные возможности, отсутствие Android-агента. |

Аргументы сравниваются строго, порядок ключей JSON не важен. Допустимые
альтернативы задаются явно в `expected`. Для поисковых строк это означает, что
семантически разумный новый вариант может потребовать ручного разбора; нельзя
добавлять исключения только для улучшения результата одного кандидата. Изменение
набора требует новой версии и повторного прогона всех сравниваемых моделей.

`routingAccuracy` измеряет правильность выбора следующей команды/категории ответа.
Для `answer`, `clarify` и `unsupported` текст **не оценивается автоматически**:
все такие совпадения попадают в `manualReviewIds`. Проверяющий читает `rubric`
соответствующего задания, отмечает pass/fail и пояснение в отдельном отчёте.
Например, ответ «уже играет» после пустого поиска не проходит ручную проверку,
даже если категория `answer` совпала. `automatedPassed` и exit code 0 не означают
пригодность модели без этой проверки.

Отчёт даёт отдельные результаты по языкам/группам, ошибки формата, пропуски,
дубли и критические случаи. Необязательные p50/p95/max задержки и памяти считаются
только по переданным измерениям; скрипт их не измеряет и не подтверждает самостоятельно.

## Выбор модели и дообучение

1. Зафиксировать версию набора, commit Wave, модель и ревизию весов, лицензию,
   квантование, inference runtime, параметры генерации и шаблон чата.
2. Выполнить baseline без дообучения с одинаковыми заданиями и контекстом. Сохранять
   исходные ответы, ошибки разбора и результаты ручной проверки, а не только процент.
3. Для начального допуска целиться в ≥95% правильных решений, 100% критических
   случаев и отсутствие ложных сообщений об успехе по ручной проверке. Это рабочие
   критерии проекта, не полученные измерения и не гарантия работы полного агента.
4. Измерять на одном ПК отдельно холодный запуск и прогретые запросы, минимум пять
   повторов. Записывать CPU, RAM, ОС, GPU (или его отсутствие), потоки, контекст,
   p50/p95 времени до готового решения, пиковую память всего дерева процесса.
   Для облака отдельно учитывать сеть; не сравнивать сетевую задержку с чистым inference.
5. Через исполнитель и контроллер диалога измерить успех завершённых задач, число шагов,
   отмену, пропуски/остановки звука и нагрузку во время воспроизведения. Минимальный
   ПК и окончательные бюджеты памяти/задержки ещё нужно определить на реальном железе.
6. Обучающие диалоги создавать отдельно, из разрешённых источников и сценариев.
   Не включать эти 60 заданий, их ответы, переводы и близкие перефразировки в обучение.
   Разделять данные по семействам сценариев, а не случайным строкам одного диалога.
7. Помимо этого публичного набора подготовить закрытый holdout до обучения и не
   использовать его для подбора гиперпараметров. Публичный v1 полезен для регрессии,
   но сам по себе не доказывает обобщение на неизвестные запросы.
8. Сравнить исходную модель, дообученную модель и конечный квантованный вариант на
   одинаковом оборудовании. Дообучение проводить отдельно от устройств пользователя.

Не обучать модель на библиотеке пользователя, токенах, URL потоков или локальных
путях. Персональные сведения должны поступать через ограниченные результаты
инструментов, а не запоминаться в весах.
