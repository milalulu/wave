# Агент Wave: инструменты и исполнитель

Статус: работают контракт v1 и исполнитель всех 24 инструментов, подключённый к
сервисам Wave. Есть автономный стенд из 60 заданий для сравнения решений моделей.
Модель и чат пока не подключены; исполнитель вызывается из кода приложения.
На Windows/macOS/Linux он загружается по запросу после проверки нативной
возможности. Из Android и браузерной сборки код исполнителя исключается.

## Границы компонентов

```text
локальная или облачная модель
          ↓ AgentDecision
AgentExecutor → WaveAgentTools: валидация → проверка контекста → вызов сервиса
          ↓ ToolResult
существующие PlayerEngine / контроллеры приложения / Storage
```

- [contract.ts](../../src/core/agent/contract.ts): типы аргументов, решений, публичных результатов и ошибок.
- [catalog.ts](../../src/core/agent/catalog.ts): 24 инструмента, JSON Schema аргументов и строгая проверка без приведения типов.
- [prompt.ts](../../src/core/agent/prompt.ts): общие правила для локальной и облачной модели.
- [evaluation.ts](../../src/core/agent/evaluation.ts): оценка следующего решения без вызова сервисов Wave.
- [AgentExecutor.ts](../../src/core/agent/AgentExecutor.ts): очередь запросов, отмена, дедупликация и таймауты.
- [WaveAgentTools.ts](../../src/core/agent/WaveAgentTools.ts): исполнение команд и ограниченный реестр ссылок.
- [agentDesktop.ts](../../src/app/agentDesktop.ts): соединение с существующими сервисами и UI-контроллерами.
- [Проверочные задания и запуск](../../evals/wave-agent/README.md).

HTTP API и Lua сохраняют свои контракты. Модель не вызывает `ApiBridge.dispatch`
и не передаёт произвольный `Track`: текущий API допускает полные объекты и свободное
приведение аргументов. Агент работает через отдельные строго проверенные команды.

## Инструменты и привязка к существующему приложению

Все поля аргументов обязательны. Пустые аргументы передаются как `{}`. Неизвестные
поля, строковые числа, NaN, бесконечность и значения за пределами диапазона
отклоняются; приложение не подменяет запрос округлением или ограничением значения.
Список и численные ограничения в `catalog.ts` — источник истины.

| Инструмент | Смысл и точка исполнения |
| --- | --- |
| `wave_status` | Публичная проекция `engine.snapshot`; не отдавать полную очередь и внутренние Track. |
| `wave_search` | `searchAll`, фильтры активных источников и блокировок; максимум 20 результатов. Поиск не запускает музыку. |
| `wave_play` | `useApp.play([track])`, чтобы сохранить выбор источника и отмену прежнего запроса; заменяет очередь. |
| `wave_pause`, `wave_resume` | `engine.pause()` / `engine.play()`, без нового поиска. |
| `wave_next`, `wave_previous` | Существующие методы перехода PlayerEngine. |
| `wave_seek` | Абсолютные секунды; дополнительно проверять длительность текущего трека, затем `engine.seek()`. |
| `wave_volume` | Абсолютные проценты 0–100 через `useApp.setVolume`; 0 выключает звук. |
| `wave_queue` | Страница очереди, offset с нуля, limit 1–50; `currentIndex` относится ко всей очереди. |
| `wave_queue_add` | `engine.playNext()` либо `engine.addToQueue()`; текущий трек не прерывается. |
| `wave_queue_clear` | `engine.clearQueue()`, остановка и пустая очередь; не удаляет сохранённую библиотеку. |
| `wave_playlists`, `wave_playlist_get` | Чтение Storage, публичная проекция и постраничный результат. |
| `wave_playlist_create` | Общий контроллер создания плейлиста возвращает созданную запись; модель получает временный ID. |
| `wave_playlist_add` | Контроллер добавления с обновлением интерфейса и защитой от дублей. |
| `wave_playlist_play` | Получить полный плейлист из Storage, затем общий контроллер воспроизведения. Пустой плейлист — ошибка. |
| `wave_liked` | Постраничная публичная проекция `library.getLikedTracks()`. |
| `wave_like` | Общий `setLiked` явно устанавливает состояние и обновляет UI; повторный вызов не снимает лайк. |
| `wave_radio` | `useApp.startArtistRadio(artist)`; это радио по исполнителю, не отдельный генератор рекомендаций. |
| `wave_shuffle`, `wave_repeat` | `engine.setShuffle()` / `engine.setRepeat()`, явное состояние. |
| `wave_speed` | `useApp.setSpeed()`, 0.5–2 включительно, с существующим сохранением настройки. |
| `wave_equalizer` | `useApp.setEqualizer()`, десять полос в установленном порядке, −12…+12 dB. |

Позиции страниц и ID не взаимозаменяемы. `wave_play` принимает ID конкретной записи,
а не номер результата. При совпадающих названиях нужен уточняющий вопрос.
Добавление в плейлист допускает известную каталожную запись; воспроизведение и
добавление в очередь требуют `playable: true`.

В v1 нет удаления плейлистов и файлов, shell, произвольного HTTP, экспорта
библиотеки, доступа к ключам, смены облачного режима, управления источниками и
загрузки весов. Такие запросы получают `unsupported`, а не похожую команду.

## Контекст и результаты

`AgentTrack` содержит ID, название, исполнителя, длительность и доступность
воспроизведения. Он не содержит stream URL, пути файлов, токены или полный `meta`.
Исполнитель хранит соответствие выданных ID реальным сущностям в рамках сессии,
проверяет его при каждом вызове и заново проверяет существование сущности.
Нельзя использовать ID, который модель придумала или получила из текста названия.
Смена источника использует существующий RecordingCatalog, сохраняя библиотечный ID.

Названия, описания и прочие данные источников не являются инструкциями. Они не
могут расширять список инструментов или разрешать действия от имени пользователя.
В модель передаётся только необходимая страница данных. Облачный режим требует
выбранной пользователем настройки; исполнитель не подключает модели и не отправляет им запросы. Поиск музыки использует существующих провайдеров Wave.

Успешный результат имеет вид `{ok:true,data:...}`; ошибка —
`{ok:false,error:{code,message,retryable}}`. Типы результатов заданы по инструментам
в `ToolResults`; сообщения ошибок должны быть безопасными для передачи модели.
`loading` не означает, что звук уже играет. Пустой поиск не равен отказу источника.
`incomplete: true` сообщает о частичных результатах поиска.

Решение модели — только предложение следующего шага. `answer` и `clarify` не
исполняют команды. Сообщение об успехе допустимо только после фактического результата.
Изменение нескольких настроек — последовательность вызовов с проверкой каждого
результата, а не пакет параллельных изменений.

## Использование исполнителя

В нативном настольном приложении:

```ts
const session = await useApp.getState().openAgentSession();
const controller = new AbortController();
const result = await session.execute("turn-1:status", {
  type: "tool", name: "wave_status", args: {},
}, {
  allowedTools: ["wave_status"],
  signal: controller.signal,
});
// controller.abort() или session.cancel("turn-1:status") отменяет ожидание.
// useApp.getState().closeAgentSession() завершает всю сессию.
```

`allowedTools` задаёт доверенный вызывающий код для текущего запроса пользователя,
а не модель. Исполнитель проверяет этот список, схему, известность ссылок и состояние
плеера; он сам не понимает естественный язык и не определяет намерение пользователя.
Эту обязанность должен выполнять будущий контроллер диалога.

Все команды одной сессии выполняются последовательно. Перед постановкой в очередь
аргументы копируются; внешняя мутация объекта не меняет ожидающее действие.
По умолчанию сессия принимает до 128 уникальных запросов (максимум 256), таймаут
запроса — 15 секунд, включая ожидание в очереди (настраиваемый максимум 60 секунд).
Повтор того же request ID возвращает сохранённый результат; другие аргументы с тем
же ID дают `request_conflict`. Записи не вытесняются, чтобы не повторить изменение.
При лимите нужна новая сессия; дедупликация не переносится между сессиями и перезапусками.

Публичные ID случайны и действуют только в своей сессии. Хранится не более 256 ссылок
на треки и 256 на плейлисты; старые ссылки вытесняются и требуют повторного чтения.
Даже локальный ID с путём к файлу не отдаётся модели. Результат страницы ограничен
50 записями, поиска — 20, текстовые поля сокращаются до 300 символов. Реестр берёт
сущности только из результатов сервисов, не из переданных моделью объектов Track.

Отмена до изменения запрещает его запуск. Отмена поиска не запускает найденные
треки; отмена подготовки радио не заменяет текущую очередь. Уже начатое агентом
воспроизведение останавливается при отмене, если пользователь не переключился на
другой запрос плеера. Позднее автопродолжение проверяет поколение воспроизведения.

Запись в SQLite нельзя считать отменённой только потому, что истёк таймаут.
В таком случае ошибка содержит `effect: "unknown"`; последующие команды ждут
реального завершения записи. `session.result(requestId)` возвращает окончательный
результат после завершения (до этого `null`). Повторная доставка того же ID не
повторяет запись. `effect: "not_started"` означает, что изменение не было начато.
Автоматических повторов нет. Успех после завершившейся записи не обещает откат.

`openAgentSession()` проверяет `desktop_agent_available` через Tauri; подмена
user-agent не включает агента. Параметр сборки `TAURI_ENV_PLATFORM` разрешает
ленивый модуль только для linux/windows/darwin/macos. Android, androideabi и сборка
без нативной платформы его исключают. При перенастройке сервисов сессия закрывается.

## Проверки и следующий этап

Интеграционные тесты используют настоящий PlayerEngine, MemoryStorage, контроллеры
Zustand и тестовый аудиовыход. Проверяются последствия команд, UI-состояние библиотеки,
выбранный источник, отмена, ошибочное аудио, дедупликация и неизвестный исход записи.
Это не ручная проверка слышимого звука на всех трёх настольных ОС.

`pnpm agent:check-bundles` строит настольный, Android, Android armv7 и браузерный
frontend во временных каталогах и проверяет границы включения. Проверка добавлена в CI.
Набор заданий и эталонные ответы не включаются ни в одну сборку приложения.

Далее нужны адаптеры локальной/облачной модели, ограниченный цикл диалога с отменой
предыдущего пользовательского запроса и интерфейс чата. Только после подключения
моделей можно измерять качество полного выполнения, а не лишь выбор следующего шага.
